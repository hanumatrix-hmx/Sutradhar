== NEW INSTANCE 1 (critical): hidden wait falsely SUCCEEDS when the tab closes mid-wait ==
browser-action-engine.ts:1477-1485 (pierceFirstMatch). On tab close, frame.$ can reject with "Execution context was
destroyed". isContextDestroyedError() classifies this as a "recoverable in-page navigation hiccup" and returns
{kind:'no-match'}. isHiddenInEveryFrame then returns 'hidden', and the wait reports success with matchedAtStart:true.
liveFramesOf's page.isClosed() guard (GAP-031) only fires on the NEXT pass. The close races the in-flight probe of
the CURRENT pass, and that probe's error is misread as a confirmed negative.
Same shape one level down: isHandleVisible:1616 maps context-destroyed to 'not-visible'.
Live:
  MCP (probe-a6 T): 1/30, then 3/60 (probe-a6-T-run2.log). In each case: correct tabId, #stay observer-confirmed
    visible just before close, success returned 228-436ms after the wait started (right after the close,
    not at the 2000ms timeout).
  Engine-direct with a prototype-wrapper trace (diag-tabclose.mjs): 1/80. Trace:
    raceFrameProbe threw "Execution context was destroyed" -> pierceFirstMatch {kind:'no-match'} -> isHiddenInEveryFrame "hidden"
This is GAP-031 / GAP-081's exact user-visible bug (false hidden success on tab close), surviving through a third
classification branch that no inventory examined. Mutation a6-N3 (context-destroyed -> 'unknown') passes all 227
browser tests, so nothing guards this behaviour.

== NEW INSTANCE 2 (major): visible-wait timeout says "none is visible" while an unanswered frame holds a VISIBLE match ==
browser-action-engine.ts:2086-2116 (describeWaitForSelectorTimeout). fix-4's GAP-083 guard (:2078) only handles
total===0 && unconfirmedFrames>0. Once ANY frame answered (total>0), unconfirmedFrames is ignored. The message then
asserts "N element(s) match ... but none is visible", and MCP appends "Hint: The element exists but is hidden."
Frames that never answered are silently treated as confirmed not-visible: the same asymmetry fix-4 closed for
total===0.
Live (ground truth read from each frame BEFORE it was made busy):
  C2a: #x hidden in main, VISIBLE #x in a busy OOPIF. Wait and check-once both give "none is visible" + hint. 2/2.
  C2b: VISIBLE #x in a busy MAIN frame, hidden #x in an OOPIF. Wait and check-once both give "none is visible" + hint. 2/2.
  SDK surface (sdk-c2.mjs, SDK's own default Chrome launch): C2a gives the same false message. 2/2.
  CLI: prints `Wait failed: ${result.error}` verbatim (cli.ts cmdWait), so it gets the same engine text (by code read).
audit-5's A6 had the same setup with no match in the busy frame, and it was judged "correct" only because of
ground truth that the tool could not have known.

== NEW INSTANCE 3 (major): MCP hint "The element is still visible." appended to a probe ERROR ==
tools.ts ERROR_HINTS 'waiting for state=hidden' entry. Its `unless` list only covers 'could not verify' and
'could not determine'. The engine's OTHER hidden-state failure family, "wait_for_selector failed waiting for
state=hidden: <raw error>" (engine :853-855 and :1843-1845), also contains 'waiting for state=hidden'. So a
Target-closed, Session-closed or "Tab was closed" probe error reaches MCP users with a confident "The element is
still visible."
Live:
  C1: #banner display:none the WHOLE time, an unrelated iframe churning every 15ms. 3/30 calls failed with
    "...failed waiting for state=hidden: Protocol error (Runtime.callFunctionOn): Target closed
     Hint: The element is still visible." That is a false claim about a genuinely hidden element.
  T: 57/60 tab-close failures carry the same unfounded hint.
This also refutes fix-5's GAP-114 judgement that isFatalFrameCheckError's over-matching yields "only hard failures,
0 false answers". That holds at the engine layer, but on the MCP surface every one of those hard failures carries a
false definite claim. So GAP-114 is not purely a robustness issue on the user-facing surface.
