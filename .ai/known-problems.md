- **ID**: `PROB-044`
  - **Summary**: `click_by_text`'s XPath used `contains(text(), ...)`, which only matches an element's DIRECT text-node children — it structurally could not find a phrase split across sibling elements, e.g. a search-results UI wrapping each matched query word in its own `<mark>` (extremely common on the modern web for highlighting search terms). No single node's own text ever contained the full phrase, even though it read as one continuous phrase and correctly appeared in `snapshot`'s own `pageText`.
  - **Severity**: Medium — `click_by_text` failing outright ("No element found containing text") on a real, common, everyday UI pattern (highlighted search results) is a real usability gap for exactly the kind of task an agent does often (search, then click the top result).
  - **Status**: RESOLVED 2026-08-18
  - **Impact**: Found live during a WebBench sample task against `frontiersin.org`'s real search results page (Milestone 95). The target article title rendered as `"...of "` + `<mark>artificial</mark>` + `<mark>intelligence</mark>` + `" in "` + `<mark>healthcare</mark>` + `"..."` — `click_by_text("...artificial intelligence in healthcare...")` failed with "No element found containing text" even though the exact phrase was visibly present as one continuous line and appeared correctly in `snapshot`'s `pageText`. Root-caused by direct inspection, not guessed: confirmed via `document.querySelectorAll` that no single leaf element's `.textContent` contained the substring, then found the actual DOM structure (`<div class="title">...<mark class="highlighted">artificial</mark>...`) confirming the highlighting-wrapper theory, then traced the exact XPath (`contains(text(), ...)`) in `browser-action-engine.ts` that explains it precisely (XPath's `text()` returns only direct text-node children, never concatenated descendant text).
  - **Mitigation**: Changed the XPath to `contains(., "...")` (concatenated descendant text, equivalent to `.textContent`) combined with `not(.//*[contains(., "...")])` — the standard XPath idiom for "the deepest/most specific element containing this text," since `contains(., ...)` alone would over-match every ancestor up to `<html>` (ancestors always contain all descendant text). Scoped fix — `contains(text()` had exactly one call site in the codebase, `click_by_text` itself; no other tool shares the pattern. `packages/browser` 187/187 (1 new regression test asserting the constructed XPath string uses the new pattern and never regresses to `contains(text(),`). Live-verified against the exact real page that surfaced the bug, via direct `SutradharRuntime` scripting (not the potentially-stale connected MCP session): `clickByText("artificial intelligence in healthcare in Saudi Arabia")` now succeeds (`success:true`, `verified:true`) and opens a new tab landing on exactly the correct article (`10.3389/frai.2025.1518440`), matching the title/DOI independently confirmed via direct URL navigation earlier in the same investigation.

## Documented technique — filling a group of related masked payment fields (Stripe Elements and similar)

Found live (2026-08-16), see `PROB-025`. When filling several related masked/actively-validated
iframe fields in the same group (a card number + expiry + CVC set is the canonical real-world
case), do **not** trust each field's own individually-reported `type` success in isolation —
typing into a *later* field in the group can retroactively corrupt an *earlier* field's
already-verified value (Stripe's shared internal Card Element state re-derives a sibling field's
display from its own internal model, which can lag behind fast synthetic keystrokes). Take one
final `browser.snapshot` covering the whole group after all fields are filled, and re-check every
field's value together before proceeding (e.g. before clicking Pay) — this reliably surfaces the
corruption where a per-field check cannot.

## Documented technique — modern editors that don't use a plain `<textarea>`/`<input>` (Monaco/`EditContext` API)

Found live (2026-08-16) testing Monaco Editor (VS Code's web editor) — not a bug, a real technique worth recording since it isn't obvious. Modern Monaco doesn't use a plain `<textarea>` for input — it uses the `EditContext` Web API, whose real focus target is an invisible, zero-box `<div class="native-edit-context">`. `click`/`type` correctly REFUSE to act on it ("Node is either not clickable or not an Element" — no box model to click, a correct refusal, not a bug). The working technique: target the visible rendered surface (`.monaco-editor .view-lines`, a real, sizable, clickable div) for both `click` and `type` — Puppeteer's real synthetic keyboard events reach Monaco's model correctly through it once focus is established (verified via `monaco.editor.getEditors()[0].getValue()` genuinely containing typed text, not a fabricated success report). Separately: a `snap` taken immediately after navigation surfaced a `<textarea aria-label="Editor content">` that looked like the obvious target but was a transitional element from Monaco's pre-`EditContext`-init state, gone moments later — a concrete, real example of why the `settle` option (Milestone 38) matters when acting on a heavy JS framework right after navigation.

- **ID**: `PROB-040`
  - **Summary**: Two compounding bugs in permission granting: (1) `grant_permissions`/`set_geolocation` silently REVOKED every previously-granted permission on an origin whenever either was called again, since CDP's `Browser.grantPermissions` replaces an origin's whole permission set rather than adding to it; (2) requesting `'clipboard-write'` specifically never actually worked at all — Puppeteer maps it to a CDP permission that does NOT satisfy `navigator.permissions.query({name:'clipboard-write'})`, so a real page's own `navigator.clipboard.writeText()` (the standard "Copy to Clipboard" button pattern) threw "Write permission denied" even immediately after an explicit grant.
  - **Severity**: High — bug (1) meant calling `set_geolocation` after granting camera/clipboard/notifications for the same origin silently broke those other permissions with zero indication; bug (2) meant `clipboard-write` was, in practice, never actually grantable at all via the documented mechanism, breaking one of the most common real page-level UI patterns (copy-code/copy-coupon/copy-share-link buttons).
  - **Status**: RESOLVED 2026-08-17
  - **Impact**: Found live testing a real "Copy to Clipboard" button (`navigator.clipboard.writeText()` in a click handler, not Sutradhar's own `set_clipboard` tool) after granting `['clipboard-read', 'clipboard-write']` — the click succeeded, but the page's own promise rejected with "Failed to execute 'writeText' on 'Clipboard': Write permission denied." Root-caused via a live diagnostic sequence, not guessed: confirmed `clipboard-write` reads as `'granted'` by Chrome's own default *before any grant call at all*; confirmed calling `overridePermissions` with an UNRELATED permission (`geolocation` alone) also flipped it to `'denied'`, proving bug (1) isn't clipboard-specific — any single-permission grant call resets the whole origin; confirmed granting `'clipboard-write'` explicitly still left it `'denied'`, while granting `'clipboard-sanitized-write'` instead correctly reported `'granted'`, proving bug (2) — Puppeteer's friendly-name mapping (`'clipboard-write'` → CDP's `clipboardReadWrite`) doesn't satisfy the actual Permissions API check, which is gated by the separate `clipboardSanitizedWrite` CDP permission.
  - **Mitigation**: Added `grantedPermissionsByOrigin` (`SutradharRuntime`, keyed `${sessionId}::${origin}`) tracking the full accumulated permission set per origin; `grantPermissions` and `setGeolocation`'s internal auto-grant now both route through a shared `applyPermissionGrant` helper that unions new permissions into the tracked set and always re-passes the FULL set to `overridePermissions`, making grants additive instead of replacing.
